# Kafka и ClickHouse

Итоговый CSV: [results/max_by_state.csv](results/max_by_state.csv). Замеры: [results/README.md](results/README.md).

Загружаю весь `test.csv` из соревнования teta-ml-1-2025 в Kafka. ClickHouse читает топик через Kafka Engine и сохраняет транзакции в MergeTree. Для каждого значения `us_state` запрос возвращает категорию самой большой отдельной транзакции и ее сумму.

```text
csv -> producer.py -> transactions_ch -> Kafka Engine -> transactions_base
                                                          |
                                                          v
                                               transactions_optimized
                                                    + by_state
```

Вторая таблица получает строки через materialized view от первой. Обе хранят все исходные столбцы. Базовая таблица нужна для сравнения, в оптимизированной изменены типы, сортировка, сжатие и добавлена агрегатная проекция.

## Запуск

Нужны Docker Desktop с Docker Compose и архив `teta-ml-1-2025.zip` из Kaggle. Архив положи в `~/Downloads`. Из папки проекта:

```bash
git clone https://github.com/zorkina/fraud-clickhouse.git
cd fraud-clickhouse
bash start.sh
```

Скрипт извлечет `test.csv`, соберет контейнер с Python, поднимет Kafka и ClickHouse, выполнит SQL создания таблиц и отправит все строки. Потом сверит данные и сохранит результаты в `results`.

Другой путь к архиву:

```bash
bash start.sh /путь/к/teta-ml-1-2025.zip
```

Также можно заранее положить `test.csv` в `data`. Если архива нет, но рядом сохранился проект первой домашки, скрипт скопирует `../fraud-kafka/data/test.csv`. Файл первой домашки не меняется.

Для исходного набора ожидается 262 144 сообщения и по 262 144 строки в каждой таблице. В результате 51 строка, так как среди значений `us_state` есть DC. Это не 51 штат.

Проект называется `fraud-clickhouse`, у него отдельные контейнеры, сеть и volumes. Порты на хост не открываются. Интерфейс и модель для этого задания не нужны. Логин `student` и пароль `fraud_local` используются только внутри локальной Docker-сети.

## Формат сообщений

Одна строка CSV становится одним JSON-сообщением. Сохраняются все 17 исходных столбцов, добавляется `row_id`, номер строки начиная с 1. Он используется как ключ Kafka и для проверки повторов. В заголовке сообщения хранится SHA-256 исходного файла.

Сумма передается десятичной строкой и хранится в `Decimal(18, 2)`, без перевода через Float64. `post_code` остается строкой. Время в исходном файле не содержит часового пояса. Оно записывается без сдвига в `DateTime('UTC')`, UTC здесь выбран только для одинаковой интерпретации на разных машинах.

Некорректные и пустые значения не заменяются придуманными данными. Проверка останавливает запуск до отправки. Число пропускаемых некорректных сообщений Kafka Engine равно нулю.

У топика одна партиция. Для этого набора достаточно одного consumer. Это также сохраняет порядок строк при продолжении прерванной отправки.

## Запрос

Пункты 2 и 3 в условии совпадают. Используется один запрос, отдельно сохранены его версии для двух таблиц.

`argMax` возвращает `cat_id` строки с максимальным `amount`. Это максимум отдельной транзакции, суммы по категориям не складываются. При равной сумме выбирается строка, которая раньше встретилась в CSV: второй элемент сравниваемого tuple равен `-row_id`.

В результат записываются `us_state`, `cat_id`, `max_amount`. Порядок строк по `us_state`.

## Оптимизация

В исходной таблице строки упорядочены по `row_id`, категориальные поля имеют тип `String`. В оптимизированной:

- Повторяющиеся значения продавца, категории, пола, города, штата и профессии хранятся как `LowCardinality(String)`. Для ряда других столбцов добавлен ZSTD, для времени и номера строки также Delta.
- Порядок хранения изменен на `(us_state, transaction_time, row_id)`. Месячные партиции не добавлялись: запрос не фильтрует даты и должен обойти весь набор.
- Проекция `by_state` хранит агрегатные состояния `argMax` и `max` по штату. При запросе ClickHouse может прочитать эти состояния вместо всех транзакций. После объединения частей состояний примерно столько же, сколько групп.

Основное уменьшение чтения для этого запроса ожидается от проекции. Один только ORDER BY не отменяет полный проход при группировке без фильтра. Цена проекции: дополнительное место и вычисления при вставке. Сохранение двух таблиц тоже увеличивает общий объем, базовая копия оставлена только для сравнения.

## Проверка и результаты

`start.sh` запускает модульные тесты и затем проверяет реальную цепочку Kafka -> ClickHouse. Модульные тесты сами по себе не проверяют работающие контейнеры.

В каждой таблице проверяется число строк и уникальность `row_id`. Все 18 полей всех строк, включая технический номер, сравниваются с CSV. Деньги сравниваются точно, координаты с допуском `1e-10` из-за текстового представления Float64. После этого результаты обоих SQL сравниваются с независимым проходом по CSV в Python.

Файлы появляются только после реального запуска:

| Файл в `results/` | Содержимое |
|---|---|
| `max_by_state.csv` | Итог SQL в ClickHouse после оптимизации |
| `max_by_state_base.csv` | Итог SQL до оптимизации |
| `benchmark.csv` | Все измерения запросов и их query_id |
| `benchmark_summary.csv` | Медианы времени и объема чтения |
| `storage.csv` | Число строк, частей и размер таблиц |
| `query_plans.txt` | EXPLAIN для трех вариантов |
| `check.json` | Контрольная сумма CSV, версия ClickHouse и итог проверки |
| `README.md` | Фактические результаты запуска и пояснение замеров |

Сравниваются три варианта: исходная таблица, оптимизированная с отключенной проекцией, оптимизированная с включенной проекцией. У всех одинаковый SQL, кроме имени таблицы, и `max_threads=2`. Query cache отключен. После прогрева выполняется по 7 измерений, порядок чередуется. Время сервера, прочитанные строки, байты, память и факт использования проекции берутся из `system.query_log`. Также измеряется время клиента с HTTP.

Перед замером обе таблицы объединяются через `OPTIMIZE FINAL`, чтобы сравнивать одинаковое количество частей. Это действие для эксперимента после конечной загрузки, не рекомендация постоянно выполнять его в работающем сервисе. Query cache выключен, но кеши ОС специально не очищаются, то есть сравниваются прогретые запросы. Если ClickHouse не использовал проекцию, проверка остановится, вместо того чтобы приписать ей ускорение.

Результаты выполненного запуска находятся в `results/`. Данные Kaggle остаются локально.

## Отдельные команды

После первого запуска отправку можно вызвать отдельно:

```bash
docker compose run --rm tools python -m app.producer --csv data/test.csv
```

Модульные тесты без запуска Kafka и ClickHouse:

```bash
docker compose build tools
docker compose run --rm --no-deps tools python -m unittest discover -s tests -v
```

Выполнение итогового SQL вручную:

```bash
docker compose exec -T clickhouse clickhouse-client --user student --password fraud_local --format CSVWithNames < sql/05_max_by_state.sql
```

## Повторный запуск

```bash
bash start.sh
```

Уже подтвержденные сообщения повторно не отправляются. Скрипт читает конец Kafka-партиции, проверяет контрольную сумму файла и последнюю строку, затем при необходимости продолжает со следующей. Одновременная отправка двумя копиями скрипта заблокирована файловой блокировкой.

Это не гарантия exactly-once всей цепочки. После аварии ClickHouse Kafka Engine может повторно обработать блок. Проверка обнаружит дубли и остановится, автоматически удалять данные она не будет. Если были вручную очищены volumes, изменен топик или загружен другой файл, не смешивай их с текущим набором.

Логи и остановка:

```bash
docker compose ps -a
docker compose logs --tail=100 kafka clickhouse
docker compose down
```

Обычный `down` сохраняет данные. Скрипт не очищает volumes и не публикует код на GitHub.
