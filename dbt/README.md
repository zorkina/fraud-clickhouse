# Аналитика транзакций в dbt

Проект строит шесть витрин в ClickHouse:

```text
transactions_db.transactions -> staging.stg_transactions -> marts
reference.states ------------------------------------------^
```

Источник данных: [teta-ml-1-2025](https://www.kaggle.com/competitions/teta-ml-1-2025). Используется полный `train.csv`: 786 431 транзакция, 4 504 метки фрода. В `test.csv` нет `target`, поэтому для этих витрин он не подходит.

## Запуск

Требуются Docker с Compose и архив `teta-ml-1-2025.zip` из Kaggle. Рекомендуется выделить Docker 6-8 GB памяти.

```bash
git clone --branch hw4-dbt https://github.com/zorkina/fraud-clickhouse.git
cd fraud-clickhouse
bash dbt/start.sh /полный/путь/к/teta-ml-1-2025.zip
```

Вместо архива можно положить `train.csv` в `dbt/data/` и выполнить `make start`.

Скрипт создает отдельный ClickHouse, загружает источник, запускает dbt, тесты и SQLFluff. Затем сверяет витрины с расчетом по CSV, генерирует документацию и сохраняет скриншоты. Повторный запуск с тем же файлом не добавляет строки в источник еще раз.

Документация: http://localhost:8084. ClickHouse: `127.0.0.1:8124`, пользователь `student`, пароль `fraud_local`. Это учетные данные локального стенда. Существующие контейнеры и базы других проектов не изменяются.

Версии: Python 3.11, ClickHouse 25.8.33.6, dbt-core 1.10.13, dbt-clickhouse 1.9.6, SQLFluff 3.4.2. Python-зависимости закреплены в `requirements.txt`, версии dbt-пакетов в `packages.yml`.

## Модели

| Модель | Гранулярность и метрики |
|---|---|
| `stg_transactions` | Одна строка на транзакцию. Типы, нормализация строк, идентификаторы, дата, час, день недели и сегмент суммы |
| `mart_daily_state_metrics` | Дата и штат: количество, сумма, средний чек, P95, количество и доля крупных транзакций |
| `mart_fraud_by_category` | Категория: количество транзакций и фродов, fraud rate, общая сумма и сумма фрода |
| `mart_fraud_by_state` | Штат: fraud rate, суммы, число уникальных клиентов и мерчантов |
| `mart_customer_risk_profile` | Клиент: начало и конец истории, активные дни, количество транзакций, fraud rate, средний чек и уровень риска |
| `mart_hourly_fraud_pattern` | День недели и час: fraud rate, суммы, отношение к общей доле фрода и признак повышенного риска |
| `mart_merchant_analytics` | Мерчант: оборот, число клиентов, fraud rate и флаг подозрительности |

Все связи объявлены через `source()` и `ref()`. Модели материализуются как таблицы MergeTree. Справочник `states` содержит 50 штатов и DC. Описания моделей, колонок и тестов находятся в YAML рядом с моделями.

## Правила расчета

Суммы в staging приводятся к `Decimal(18,2)` через строковое представление Float64. Отрицательные суммы не обнуляются и не отбрасываются: загрузчик и тесты отклоняют такие данные.

Макрос `amount_bucket` делит суммы на `SMALL` до 100, `MEDIUM` от 100 до 1000 и `LARGE` от 1000 включительно. P95 рассчитывается функцией `quantileExactInclusive` с линейной интерполяцией. Все доли фрода и крупных транзакций выражены в процентах от 0 до 100. Только при расчете долей числитель и знаменатель переводятся в Float64; сами суммы остаются Decimal.

`customer_id` составляется из нормализованных имени, фамилии, пола, штата и координат. В источнике нет банковского ID клиента, поэтому это приближение: совпадающие данные могут объединить разных людей, изменение адреса может разделить историю одного человека. `transaction_id` строится по добавленному `row_id`, номеру строки CSV. Одинаковые по содержимому транзакции автоматически не удаляются.

Время используется как записано в файле. UTC задан для одинаковой интерпретации на разных машинах, без пересчета в местное время каждого штата. Дни недели: понедельник 1, воскресенье 7.

Пороговые правила заданы в `vars` файла `dbt_project.yml`:

| Признак | Правило |
|---|---|
| Риск клиента `HIGH` | Не менее 20 транзакций и fraud rate от 5% |
| Риск клиента `MEDIUM` | Есть фрод, но условие `HIGH` не выполнено |
| Риск клиента `LOW` | В наблюдаемой истории нет фрода |
| Подозрительный мерчант | Не менее 30 транзакций и fraud rate от 2% |
| Рискованное временное окно | Не менее 100 транзакций, есть фрод и его доля не ниже удвоенной доли по всему набору |

Это выбранные правила анализа истории, не обученная модель прогнозирования. Метки берутся только из `target`. Префикс `fraud_` в названии продавца не используется как метка. При нулевой сумме или полном отсутствии фрода соответствующее отношение принимается равным нулю.

## Пакеты и тесты

`dbt_utils` используется для ключей и тестов уникальности составного ключа. `dbt_date` вычисляет день недели через ClickHouse-реализацию dispatch-макроса. `dbt_expectations` проверяет диапазоны значений и непустую таблицу.

Generic tests проверяют `not_null`, `unique`, `accepted_values`, связи со справочником и уникальность ключей витрин. В `tests/` находятся 8 singular tests: отрицательные суммы, границы долей, сохранение строк и сумм, согласованность метрик, сегменты риска и перцентиль.

В `models/unit_tests.yml` описаны 10 нативных dbt unit tests. Небольшие входные таблицы из `tests/fixtures/` проверяют границы сегментов, ISO-дни недели, P95, группировку, уникальные сущности, правила риска и деление на ноль. Эти файлы используются только в тестах.

Отдельный Python-расчет сверяет все группы всех шести витрин с исходным CSV. Для клиента сравнивается полный набор метрик без привязки к техническому хешу. Деньги сравниваются точно, значения Float64 с допуском.

После запуска в `evidence/` сохраняются:

| Файл | Содержимое |
|---|---|
| `dbt-test.log`, `dbt_test_results.json` | Фактические результаты data tests и unit tests |
| `sqlfluff.log` | Результат линтинга |
| `reconciliation.json` | Независимая сверка витрин |
| `versions.json`, `check.json` | Установленные версии и итог проверки |
| `dbt-dag.png`, `dbt-docs.png` | Скриншоты графа и страницы dbt Docs |

SQLFluff использует диалект ClickHouse и dbt templater. Ошибки компиляции не пропускаются. Pre-commit запускает тот же линтер в Docker.

## Отдельные команды

Из корня репозитория:

```bash
make test
make lint
make docs
```

Стандартные команды dbt доступны из каталога `dbt/`:

```bash
docker compose run --rm tools dbt deps
docker compose run --rm tools dbt seed
docker compose run --rm tools dbt run
docker compose run --rm tools dbt test
docker compose run --rm tools dbt docs generate
docker compose up -d docs
```

Подключение pre-commit после установки проекта, из корня репозитория:

```bash
python3 -m pip install pre-commit==4.3.0
pre-commit install
```

Остановка: `make stop`. Данные сохраняются в Docker volume. Исходный CSV, каталог `target` и скачанные пакеты в Git не включаются.
